# Lộ trình cả nhóm cùng xây core Harness

**Cập nhật Sprint 3:** gộp nội dung các chặng **3 và 4–5** trong bảng dưới thành một sprint. Xem [Sprint 3 — Source thật, tools và tool calling](sprints/sprint-03.md) để biết phân công A–D và phần bổ sung từ Sprint 2. Các số chặng trong bảng vẫn giữ theo lộ trình ban đầu để đối chiếu; lịch các chặng tiếp theo sẽ được cập nhật khi nhóm chốt.

| Sprint dự kiến | Bốn người cùng code | Nghiên cứu pipeline và audit | Đầu ra và điều kiện chuyển chặng |
|---|---|---|---|
| **1** | **Chốt luồng core và cách dùng lại OpenCode.** Thống nhất run, snapshot, model request/response, tool call/result, verdict và event. Chọn một provider/model đầu tiên, cách cấu hình API key và giới hạn gọi API. Xác định phần OpenCode cần tham khảo hoặc tái sử dụng. | Phác pipeline Judge và Audit, phần dùng chung/riêng, bằng chứng cần có và điều kiện kết luận. Đối chiếu contract với blueprint, ghi quyết định còn mở. | Cả nhóm giải thích được một run từ đầu đến cuối và thống nhất contract tối thiểu. Có phạm vi gọi model thật ở sprint 2 và ngân sách dự kiến. |
| **2** | **Dựng nền core và gọi model thật ngay.** Thiết lập repo nhiều package bằng Bun/Turborepo, public exports, cấu hình và cách ghép các thành phần. Kết nối PostgreSQL/Drizzle, tạo migration đầu tiên. Viết adapter API thật trong `llm` và runner một lượt trong `core`: nhận yêu cầu → gọi model → ghi kết quả hoặc lỗi. Lưu dữ liệu thực tế qua các operation có thể tiếp tục dùng ở những chặng sau. | **TV6 và researcher cùng nghiên cứu Judge/Audit đến chặng agent loop.** Đọc source/phương pháp, phác hai pipeline và ca minh họa; chỉ ra phần dùng chung/riêng, giả định và dữ liệu trace cần ghi. Đối chiếu request/response thật với B/C/D; bàn giao bản đầu ngay trong sprint. | Một lệnh khởi động core; gửi prompt đơn giản tới model thật; lưu mã lượt chạy, cấu hình, trạng thái, event và từng attempt rồi đọc lại sau khi khởi động lại. Có timeout, giới hạn output/chi phí và profile được chốt trước khi gọi; SDK không retry ngầm. Hai người nghiên cứu nhận contract và trace để đối chiếu pipeline. Đây là luồng gọi model đầu tiên, chưa công bố verdict Judge khi chưa có source và evidence validation. |
| **3** | **Nhập source và nối vào luồng chạy hiện có.** Repository registration, snapshot bất biến, inventory/digest, đường dẫn nội bộ, quyền đọc và vòng đời tài nguyên. Cấp snapshot cho run; đưa một phần source được phép đọc vào request của model qua public operation của `source_access`. | Hai người làm rõ source mỗi mode được thấy, cách chọn phạm vi đọc và evidence gắn với snapshot. Rà nguy cơ lộ ground truth/secret; cập nhật hai pipeline và yêu cầu source cho đội code. | Tạo snapshot từ repository thật; source gốc đổi không làm đổi snapshot. Run chỉ dùng ID snapshot; raw host path không vào request model hoặc trace. Traversal, symlink vượt phạm vi và dữ liệu ngoài quyền bị chặn. Model nhận được source từ snapshot đã đăng ký. |
| **4–5** | **Tool đọc và tool calling với model thật.** Tool definition, schema, registry, dispatch, các tool đọc/tìm kiếm tối thiểu; kiểm tra quyền trước I/O, timeout và output limit. Mở rộng runner để nhận tool request từ model, thực thi tool trong snapshot và gửi kết quả lại cho model trong một chuỗi ngắn có giới hạn. | Hai người đối chiếu từng bước Judge/Audit với tool thực tế: cần đọc/tìm gì, nhận kết quả gì, xử lý lỗi và thiếu bằng chứng ra sao. Review chéo ca minh họa, cập nhật pipeline và bàn giao yêu cầu cho chặng context. | Model thật yêu cầu đọc source → runtime thực thi tool → model nhận kết quả và phản hồi tiếp. Input sai, tool không đăng ký, file thiếu/lớn và truy cập trái phép có lỗi rõ ràng. Tool request/result và từng model attempt được lưu; Judge chỉ có quyền đọc. |
| **6** | **Context cơ bản trong luồng chạy thật.** Tách phần chuẩn bị request của runner thành thành phần quản lý context: ghép finding, instruction, history đã lưu, tool definition/result; dành chỗ cho output, kiểm tra giới hạn và cắt output có ghi nhận. Runner gọi phần này trước mỗi model attempt. | Hai người chốt bản thiết kế đủ để đội code bắt đầu agent loop: context từng bước, phần chung/riêng, đầu ra, điều kiện chuyển bước/dừng và cách xử lý lỗi. Đối chiếu request thật, giới hạn context và nguy cơ mất evidence; bàn giao trước sprint 7. | Các lượt model/tool hiện có dùng context planner chung. Request gửi đi khớp nội dung đã lưu; vượt giới hạn được xử lý trước khi gọi API. Bằng chứng nguồn và thông tin biến đổi context truy ngược được. |
| **7–8** | **Mở rộng runner thành agent loop nhiều lượt.** Dùng adapter API thật, tools, context và persistence đã có để chạy model → tool → context mới → model cho tới khi đạt điều kiện dừng. Hoàn thiện budget theo bước/token/thời gian/chi phí, no-progress, cancellation và xử lý lỗi. Retry chỉ bật theo policy rõ ràng và ghi riêng từng attempt. | Hai người đối chiếu pipeline Judge/Audit với trace của loop thật, kiểm tra điểm dừng, lặp thao tác, lỗi và ngân sách. Sửa giả định sai, bàn giao hai pipeline đã review cùng căn cứ lựa chọn và ca kiểm tra; ghi câu hỏi còn mở. Nhóm chốt phân công application/UI cho giai đoạn sau. | Run thực hiện nhiều lượt trên source thật, dừng đúng điều kiện và ghi đủ diễn biến. Không khởi động thao tác tiếp theo khi đã hết budget hoặc kết thúc run. Lỗi và timeout có kết quả rõ ràng; kết quả về muộn không ghi đè terminal state. |
| **9–10** | **Judge MVP dùng được xuyên suốt.** Ghép workflow nhận finding cùng snapshot, prompt kiểm tra finding, giải mã verdict và validation evidence. Hoàn thiện API tạo/xem run và event để application kết nối giao diện thật. Lưu verdict/evidence cùng terminal state theo transaction; phân biệt kết luận nghiệp vụ với lỗi thực thi. | Dùng bản pipeline Judge đã bàn giao ở chặng agent loop để audit ca có căn cứ, thiếu căn cứ, output sai schema/evidence và lỗi thực thi. Cập nhật thiết kế theo bằng chứng mới; đánh giá cách trình bày kết quả và trace. | Người dùng gửi finding và snapshot qua API, theo dõi run và nhận verdict có cấu trúc với evidence hợp lệ. Judge dùng model thật và dữ liệu lưu thật; kết quả trước verification là `unverified`. Lỗi hạ tầng không biến thành finding invalid. Application tạo và xem run qua public contract. |
| **11–12** | **Hoàn thiện vận hành bền vững cho Judge MVP.** Củng cố admission, idempotency, durable work/outbox, claim/lease, hủy và phục hồi. Các cơ chế tương ứng phải có từ khi đưa hàng chờ/worker vào luồng ở chặng trước; chặng này hoàn thiện cạnh tranh nhiều worker, crash/redelivery, shutdown và replay trace. | Audit gửi trùng, hủy, crash, mất kết nối DB/provider và phục hồi từ dữ liệu đã commit. Kiểm tra trạng thái nhất quán, việc ghi nhận attempt có kết quả chưa rõ và giới hạn phục hồi. | Đóng UI không làm mất hoặc tự hủy run. Nhiều worker không cùng sở hữu một việc; worker cũ không ghi tiếp sau khi mất claim. Khởi động lại đọc/khôi phục đúng trạng thái; không tự gọi lại attempt có kết quả chưa rõ. Có hướng dẫn xử lý run gián đoạn. |
| **13** | **Skills trong Judge đang hoạt động.** Cách lưu, nạp, chọn và đưa skill vào context; ghép skill đầu tiên rồi các skill đã chọn cho reentrancy, access control và oracle manipulation. Lưu phiên bản và cấu hình bật/tắt theo run. | Nghiên cứu nội dung skill, bằng chứng cần tìm và điều kiện loại trừ. Audit request/trace để xác định hướng dẫn được đưa vào và có dẫn tới kết luận thiếu căn cứ không. | Skill dùng được tools hiện có trong run thật; truy ngược được phiên bản và nội dung đã ảnh hưởng request. Có flag và telemetry để đánh giá đóng góp sau này; cải thiện precision cần được chứng minh qua đánh giá. |
| **14–15** | **Context nâng cao và memory.** Mở rộng context planner bằng session notes, chọn history, compaction; chỉ thêm memory giữa các run khi đã chốt phạm vi, provenance và reset policy. Lưu trạng thái cần thiết để phiên dài và phiên phục hồi dùng đúng context. | Audit thông tin trước/sau compaction, mất evidence, nguồn của memory và khả năng dữ liệu đi sang run khác. Đề xuất cách đo tác động tới chất lượng và chi phí. | Phiên dài với model thật giữ được finding, evidence và tiến độ công việc; truy ngược được mọi biến đổi context. Memory có phạm vi/reset rõ ràng, không mang nhãn hoặc dữ liệu trái quyền vào run. Các cải tiến có flag và telemetry. |
| **16–17** | **Audit MVP trên runtime hiện có.** Ghép workflow từ snapshot: khảo sát → tạo giả thuyết → thu thập bằng chứng → lọc/gom finding → báo cáo. Tái sử dụng model adapter, tools, context, run lifecycle và persistence; bổ sung API/report để application hiển thị kết quả. | Dùng bản pipeline Audit đã bàn giao ở chặng agent loop; rà lại sau các thay đổi về skills/context/memory. Audit phạm vi đọc, finding thiếu căn cứ, gom trùng và lý do dừng trên repository thật; hoàn thiện tiêu chí đánh giá riêng cho Audit. | Người dùng chọn snapshot và chạy Audit với model thật, nhận báo cáo có evidence và trace. Có thể đưa finding sang Judge qua contract đã chốt. Dữ liệu và giao diện phân biệt báo cáo Audit với verdict Judge. |
| **18–19** | **VerificationRunner riêng và tích hợp kết quả thật.** Dựng môi trường cô lập để build/chạy PoC, giới hạn tài nguyên và mạng, lưu bằng chứng cùng cấu hình môi trường. Nối finding từ Judge/Audit tới verification và hiển thị kết quả qua API. | Chốt ý nghĩa bằng chứng PoC, trạng thái và cách xử lý lỗi môi trường. Audit sự khác biệt giữa test chạy thành công và exploit được chứng minh, xác định phạm vi repository hỗ trợ. | Chạy được finding → verification → kết quả có bằng chứng trên repo hỗ trợ. Phân biệt xác minh được, bác bỏ có căn cứ và chưa xác minh; lỗi build/test không tự chứng minh finding sai. Judge/Audit vẫn chỉ đọc source; quyền thực thi thuộc runner riêng. |
| **20** | **Hoàn thiện bản MVP để cài đặt và vận hành.** Ghép Judge/Audit/verification với application; hoàn thiện cấu hình, đóng gói runtime, migration khi nâng cấp, backup/restore, cleanup và quan sát lỗi. Kiểm tra hồi quy/an toàn trên các luồng thật; viết hướng dẫn cài đặt, giới hạn hỗ trợ và xử lý sự cố. | Audit bản phát hành trên môi trường sạch, kiểm tra bằng chứng sửa lỗi và khả năng truy ngược kết quả. Tổng hợp giới hạn còn lại, điều kiện vận hành đã chứng minh và câu hỏi cho giai đoạn đánh giá nghiên cứu. | Người khác cài và chạy được các workflow đã hỗ trợ bằng API model thật; dữ liệu và trace tồn tại qua khởi động lại, hủy/lỗi có kết quả rõ ràng. Có quy trình migration, backup/restore và hướng dẫn vận hành đã kiểm tra. Bàn giao MVP cùng phạm vi hỗ trợ và các vấn đề còn mở; khóa phiên bản cho giai đoạn đánh giá nghiên cứu. |
