## Why

The project needs one authoritative, implementation-ready Judge-mode blueprint before any application code is scaffolded. The current planning material describes the target system, but applying this change must first turn those requirements into reviewable architecture, contracts, security controls, evaluation rules, and handoff evidence that all six tracks can implement consistently later. A comparative review of the local OpenCode repository also showed that the blueprint must freeze physical module boundaries and runtime ownership explicitly so the team can reuse sound agent patterns without inheriting a general-purpose coding agent's stack, capabilities, compatibility layers, or durability gaps.

## What Changes

- Produce a documentation-only `blueprint/` package for the Judge-mode MVP; applying this change MUST NOT scaffold application code, install runtime dependencies, create executable migrations, invoke a model provider, or run an evaluation dataset.
- Define a capability-first, multi-process modular-monolith runtime, downloadable desktop-client topology, domain ports, ownership map, dependency rules, lifecycle state machine, and end-to-end sequences.
- Freeze the accepted stack family as Python 3.12 with FastAPI, Pydantic v2, SQLAlchemy 2.x, Alembic and PostgreSQL for the local runtime, worker, evaluator and scorer; React and TypeScript on Node.js LTS with Vite for the desktop UI; Tauri 2 with a narrow Rust native host for the desktop shell; and `uv`, `pnpm`, Cargo, committed lockfiles and Docker Compose for reproducible development and local-runtime delivery. Exact compatible dependency and Rust-toolchain versions remain future lockfile/readiness decisions inside this family.
- Accept ADR-007 at architecture-choice scope: Tauri exposes only explicitly allowlisted native capabilities for runtime discovery/start-or-attach, repository selection, protected local credential mediation, notifications and coordinated signed updates. The renderer receives no generic filesystem, shell, process, credential, arbitrary-URL or updater authority. The Python/PostgreSQL runtime MUST remain supervised or detached from the window lifecycle rather than becoming a Tauri-owned child whose exit cancels work; Electron becomes a contingency requiring a superseding ADR, and Python-hosted shells are rejected for MVP.
- Define a normative physical repository layout for top-level canonical contracts, `runtime/`, `apps/desktop/`, configuration, dataset manifests, packaging, tests and future extension seams. The runtime MUST be organized capability-first across `run_control`, `model_gateway`, `source_access`, `agent_runtime`, `judge`, `evaluation`, and physically isolated `scoring`, with shallow hexagonal layers inside each capability. Business adapters and persistence ownership MUST remain inside their capability; outside capability modules the runtime may contain only the minimal shared kernel, technical platform, composition roots and generated representations of top-level canonical contracts.
- Define a downloadable desktop client plus local headless runtime as one coordinated product release. The desktop MUST use only the generated versioned local-runtime client, while daemon, worker, evaluator and scorer processes continue independently of UI lifecycle and derive authority from PostgreSQL. The local control plane MUST be non-public, access-controlled, version-negotiated and recoverable after client or process restart.
- Define explicit agent-runtime ownership: one provider-port invocation performs exactly one observable provider attempt, one tool-dispatch invocation settles exactly one local tool call, and only the Judge orchestrator owns continuation, retry decisions, context rebuild, persistence, budgets and terminal commit. Hidden SDK loops, hidden retries and provider-hosted tools are excluded from Judge MVP.
- Accept the MVP provider-integration strategy: the project-owned `ModelProvider` port remains the only orchestration contract; the first real adapter targets OpenAI Responses API through the official Python SDK; in-process gateways, external proxies and agent-framework runtimes are excluded from MVP. Exact model snapshot, capability digest, knowledge cutoff, pricing version, credential owner and paid-call ceiling remain in a separate versioned provider profile that must be accepted before any real call.
- Define PostgreSQL outbox/job-table delivery and claim/version state as the durable execution authority for the out-of-process worker. SQLite, Redis, process-local coordinators and streaming APIs are not required MVP runtime dependencies; process memory may optimize execution but may never be the source of truth.
- Define scorer isolation as a top-level capability, physical entrypoint, process identity, credential and database-role/schema boundary, not only an import convention, and require generated-client plus import-boundary drift checks in the future implementation.
- Record an explicit, provenance-traceable OpenCode adoption/rejection decision against clean local snapshot `14f0bf64a19493110b51f5fdeb9c1c1bba5dd3f5`: adopt canonical contracts, inward dependency direction, one-turn model calls, one-call tool settlement and event-driven trace ideas; adapt them to Judge-specific safety, persistence and evaluation boundaries; reject wholesale forking, source/dependency copying, automatic upstream synchronization, Bun/Effect/SolidJS coupling, the product-scale monorepo, host-authority tools, process-local durability and V1/V2 compatibility baggage. A later snapshot or any source reuse requires a new documented review and cannot silently alter the accepted architecture.
- Define implementation-neutral contracts for provider traffic, safe source tools, context budgeting, structured verdicts, trajectory events, persistence records, asynchronous local-runtime resources, downloadable desktop states, feature flags, manifests, and evaluation exports.
- Document the ground-truth trust boundary, immutable source workspace policy, threat model, redaction rules, adversarial acceptance catalog, and scorer-only data flow.
- Document an accepted direct-versus-harness methodology with paired case/repeat cells, one shared Judge core prompt, equal total logical-token budgets, no provider retry in the primary comparison, contest-aware uncertainty, predeclared precision/recall/completion conclusion gates, contest/source-family split rules, contamination buckets, ablation requirements, and reproducibility metadata.
- Record the selected stack family, OpenCode reference disposition, capability-first source architecture, desktop/local-runtime distribution, Tauri native-shell/signing/updater boundary, direct-SDK provider integration strategy, and baseline methodology as accepted blueprint decisions. Keep the packaged three-OS lifecycle/credential/update spike as readiness evidence rather than pretending ADR acceptance proves distribution, and keep the exact real model snapshot/profile plus the separately versioned confirmatory experiment profile—including frozen dataset, prompt digests, budget, repeats, schedule seed, statistical thresholds, pricing, credential owner and paid-run ceiling—as explicit execution gates. Remaining profile or experiment choices MUST NOT block production of the blueprint or the two deterministic provider profiles.
- Add bidirectional traceability from every requirement and acceptance scenario to a blueprint artifact, TV owner, validation method, and future implementation work package.
- Preserve extension points, but do not design Audit mode internals, cross-run long-term memory, compaction, or complete PoC execution in this change.

## Capabilities

### New Capabilities

- `judge-run-orchestration`: Blueprint contract for the Judge lifecycle, one-turn-at-a-time agent loop, context preflight, budgets, recovery, terminal states, capability-first physical module boundaries, and orchestration ownership.
- `provider-abstraction`: Blueprint contract for provider-neutral single-attempt invocation, direct official-SDK integration, versioned real/deterministic profiles, metadata, usage, cost, error normalization, prohibition of hidden loops/retries/hosted tools, and later real-provider expansion.
- `secure-source-tools`: Blueprint contract for immutable source snapshots, structurally read-only local tools, filesystem authorization, ground-truth isolation, redaction, and adversarial validation.
- `structured-judge-verdict`: Blueprint contract for versioned verdicts, severity semantics, confidence, rationale, evidence, and explicit unverified status.
- `trajectory-persistence`: Blueprint contract for immutable reproduction snapshots, append-only trajectories, relational records, PostgreSQL-backed durable work ownership, ordering, idempotency, and content addressing.
- `evaluation-controls`: Blueprint contract for flags, ablation readiness, accepted paired-baseline methodology, separately frozen experiment profiles, logical-token fairness, primary-run retry symmetry, shared Judge-core prompts, contest/source-family manifests, physically isolated scorer access, contest-aware inference, predeclared conclusion gates, repeats, metrics, and export.
- `asynchronous-run-api`: Blueprint contract for idempotent non-blocking submission, cancellation, status/result retrieval, event pagination, generated desktop-client compatibility, durable worker handoff, local endpoint access control, protected credential failure, version handshake, independent runtime supervision, coordinated signed update behavior, errors, and desktop/runtime lifecycle independence.
- `trace-view`: Blueprint contract and downloadable-desktop wireframe requirements for runtime discovery, submission, reconnectable partial states, ordered trace inspection, verdict/evidence review, cost, latency, security-safe presentation, and a least-authority renderer-to-native command bridge.

### Modified Capabilities

None. The repository has no existing main specifications.

## Impact

- Adds or revises planning artifacts only: OpenSpec change documents and, when applied later, a `blueprint/` documentation package containing ADRs, diagrams, schemas, examples, validation matrices, and handoff records.
- Revises the future blueprint to include the accepted stack-family ADR, accepted direct-SDK provider-strategy ADR, separate gated provider profile, OpenCode reference-disposition ADR, accepted capability-first source-layout ADR, accepted desktop/local-runtime distribution ADR, accepted Tauri 2 native-shell ADR, physical repository and process topology contracts, agent-runtime boundary rules, and corresponding traceability/validation evidence.
- Does not add application source, package manifests, runtime dependencies, database instances, queues, credentials, provider calls, contest data, or generated evaluation results.
- Establishes the future contracts shared by TV1–TV6 and the acceptance gate that a separate implementation change must satisfy.
- Supports RQ1 directly through the baseline-versus-harness protocol and preserves future seams for RQ2, RQ3, PoC verification, Audit mode, memory, advanced tools, and offline replay without claiming those features are implemented.
